## 1. 문서 개요

### 1.1 목적

본 문서는 할일 관리 웹 애플리케이션 "my-todolist"를 사용자가 실제로 어떻게 경험하는지를 시나리오 형태로 구체화한다. 도메인 개념, 엔티티, 비즈니스 규칙, 유스케이스는 이미 [1-domain-definition.md](./1-domain-definition.md) (v0.3)에 정의되어 있고, 제품 범위와 기능 요구사항은 [2-prd.md](./2-prd.md) (v0.2)에 정의되어 있으므로, 본 문서는 이를 재서술하지 않고 UC-xx/BR-xx ID로 참조하며 그 위에 "사용자 입장에서의 행동 흐름과 화면 전환"을 덧붙인다.

### 1.2 관련 문서

- 도메인 정의서: [docs/1-domain-definition.md](./1-domain-definition.md) — 엔티티(EN-xx), 비즈니스 규칙(BR-xx), 유스케이스(UC-xx) 정의
- PRD: [docs/2-prd.md](./2-prd.md) — 제품 범위, 기능/비기능 요구사항, 기술 아키텍처

## 2. 사용자 페르소나

PRD 2.2절에 따라 상세 페르소나 정의는 생략하되, 시나리오 서술의 구체성을 위해 다음 두 명의 최소 페르소나를 사용한다.

| 페르소나 | 역할 | 목표(한 줄) |
|---|---|---|
| 지우 | 대학생 | 과제·시험·아르바이트 일정을 카테고리별로 나누어 놓치지 않고 챙기고 싶다. |
| 민준 | 30대 직장인 | 업무와 개인 일정을 분리해서 관리하고, 기한이 지난 일을 빠르게 파악하고 싶다. |

## 3. 사용자 시나리오

### 3.1 회원가입 및 최초 로그인

- **관련 UC**: UC-01
- **사용자 목표**: 지우는 my-todolist를 처음 사용하기 위해 계정을 만들고 로그인하려 한다.
- **사전 조건**: 지우는 아직 계정이 없다.
- **시나리오 흐름**:
  1. 지우는 회원가입 화면에서 email과 password를 입력한다.
  2. 시스템은 입력값을 검증하고 계정을 생성한다.
  3. 계정 생성과 동시에 지우 전용 '기본' 카테고리가 자동으로 생성된다(EN-02, isDefault=true).
  4. 지우는 가입 완료 후 로그인 화면으로 이동해 방금 만든 계정으로 로그인한다.
  5. 시스템은 email·password를 검증하고 인증에 성공하면 access_token/refresh_token을 발급한다.
  6. 지우는 인증된 상태로 할일 목록 화면(초기에는 빈 목록)으로 진입한다.
- **예외/대안 흐름**:
  - 이미 등록된 email로 가입을 시도하면 시스템은 등록을 거부하고 사유를 안내한다(BR-08).
  - password가 최소 8자 형식을 만족하지 않으면 가입이 거부된다(BR-08, EN-01).
  - 로그인 시 email 또는 password가 틀리면 인증 실패 사유가 화면에 표시되고, 인증이 필요한 화면(할일/카테고리/마이페이지)에는 접근할 수 없다(BR-01).
- **완료 조건**: 지우가 인증된 상태로 서비스 내 화면을 자유롭게 이동할 수 있다.

### 3.2 마이페이지에서 이름 변경

- **관련 UC**: UC-02
- **사용자 목표**: 민준은 가입 시 대충 입력한 이름을 실제 이름으로 바꾸고 싶다.
- **사전 조건**: 민준은 로그인된 상태다.
- **시나리오 흐름**:
  1. 민준은 마이페이지로 이동한다.
  2. 화면에는 email이 읽기 전용으로 표시되고, name은 수정 가능한 입력란으로 표시된다.
  3. 민준은 name을 수정하고 저장 버튼을 누른다.
  4. 시스템은 변경된 name을 저장하고 화면에 반영한다.
- **예외/대안 흐름**:
  - 로그인하지 않은 상태에서 마이페이지 API에 직접 접근하면 요청이 거부된다(BR-01).
  - 민준이 email을 바꾸려 시도해도 email은 수정 불가 항목이므로 입력 자체가 불가능하다(BR-07).
- **완료 조건**: 변경된 name이 저장되어 이후 접속 시에도 유지된다.

### 3.3 카테고리를 만들고 할일 등록하기

- **관련 UC**: UC-03 (카테고리 관리는 UC-03/UC-04의 전제 기능)
- **사용자 목표**: 지우는 '과제'라는 카테고리를 만들고, 그 아래에 첫 할일을 등록하고 싶다.
- **사전 조건**: 지우는 로그인된 상태이며 '기본' 카테고리만 존재한다.
- **시나리오 흐름**:
  1. 지우는 카테고리 관리 화면(또는 할일 등록 폼 내 카테고리 선택 UI)에서 '과제'라는 이름으로 카테고리를 생성한다.
  2. 시스템은 동일 사용자 내 이름 중복 여부를 확인(대소문자 무시, 앞뒤 공백 제거 후 비교)하고 카테고리를 생성한다.
  3. 지우는 할일 등록 화면으로 이동해 제목, 시작일자, 종료일자를 캘린더로 입력하고 카테고리로 '과제'를 선택한다.
  4. 시스템은 종료일자가 시작일자 이상인지 검증한 뒤 할일을 저장한다.
  5. 지우는 목록 화면에서 방금 등록한 할일이 '과제' 카테고리로 표시되는 것을 확인한다.
- **예외/대안 흐름**:
  - 이미 존재하는 카테고리명으로 다시 생성을 시도하면 거부된다(BR-08, EN-02).
  - 지우가 카테고리를 지정하지 않고 할일을 등록하면 자동으로 '기본' 카테고리에 저장된다(BR-03).
  - 종료일자를 시작일자보다 이전으로 입력하면 클라이언트와 서버 양쪽에서 등록이 거부되고 오류 메시지가 표시된다(BR-05).
- **완료 조건**: 새 카테고리와 그 카테고리에 속한 할일이 함께 생성되어 목록에서 조회된다.

### 3.4 카테고리·상태별로 할일 목록 필터링하기

- **관련 UC**: UC-04
- **사용자 목표**: 민준은 '업무' 카테고리 중 기한이 지난 할일만 빠르게 확인하고 싶다.
- **사전 조건**: 민준은 여러 카테고리에 걸쳐 다수의 할일을 등록해 둔 상태다.
- **시나리오 흐름**:
  1. 민준은 할일 목록 화면에 진입하면 본인 소유의 할일만 조회된다(BR-02).
  2. 민준은 카테고리 필터에서 '업무'를 선택한다.
  3. 목록이 '업무' 카테고리의 할일로 좁혀진다.
  4. 민준은 상태 필터에서 '기한초과'를 선택한다.
  5. 시스템은 조회 시점의 오늘 날짜를 기준으로 각 할일의 상태를 계산하여(BR-06, 4.4절 판정 규칙), isDone=false이면서 종료일자가 지난 항목만 화면에 표시한다.
  6. 민준은 기한이 지난 업무를 확인하고 우선 처리 대상을 파악한다.
- **예외/대안 흐름**:
  - 필터 조건에 해당하는 할일이 없으면 빈 목록이 표시된다(별도 오류 아님).
  - 타 사용자의 할일은 어떤 필터 조건에서도 노출되지 않는다(BR-02).
- **완료 조건**: 민준이 원하는 조건(카테고리+상태)으로 좁혀진 할일 목록을 확인한다.

### 3.5 할일 수정 (완료 처리 및 일정 변경)

- **관련 UC**: UC-05
- **사용자 목표**: 지우는 완료한 과제에 완료 체크를 하고, 아직 안 끝난 과제의 마감일을 늦추고 싶다.
- **사전 조건**: 지우는 본인 소유의 할일을 하나 이상 보유하고 있다.
- **시나리오 흐름**:
  1. 지우는 목록에서 완료한 과제를 선택해 편집 화면으로 이동한다.
  2. 편집 화면에는 제목·시작일자·종료일자·카테고리·완료 여부가 모두 수정 가능한 상태로 표시된다.
  3. 지우는 완료 여부(isDone)를 체크하고 저장한다.
  4. 시스템은 변경 내용을 반영하며, 목록 화면에서 해당 항목의 상태가 즉시 '완료'로 표시된다(BR-06).
  5. 지우는 다른 과제의 편집 화면에서 종료일자를 늦춰 저장하고, 목록에서 상태가 재계산되어 반영된 것을 확인한다.
- **예외/대안 흐름**:
  - 지우가 다른 사용자의 할일 편집 화면에 URL로 직접 접근하거나 API를 직접 호출해도, 소유자가 아니므로 조회/저장이 거부된다(BR-02).
  - 종료일자를 시작일자보다 이전 값으로 수정하면 저장이 거부되고 오류 메시지가 표시된다(BR-05).
- **완료 조건**: 수정한 속성이 저장되고, 목록 화면의 상태 표시에도 즉시 반영된다.

### 3.6 할일 삭제

- **관련 UC**: UC-06
- **사용자 목표**: 민준은 잘못 등록한 할일 하나를 목록에서 지우고 싶다.
- **사전 조건**: 민준은 본인 소유의 할일을 하나 이상 보유하고 있다.
- **시나리오 흐름**:
  1. 민준은 목록 화면 또는 편집 화면에서 삭제 버튼을 누른다.
  2. 시스템은 삭제 여부를 확인(confirm)하는 절차를 보여준다.
  3. 민준이 삭제를 확정하면 시스템은 소유권을 검증한 뒤 할일을 삭제한다.
  4. 목록 화면에서 해당 항목이 즉시 사라진다.
- **예외/대안 흐름**:
  - 확인 절차에서 취소를 선택하면 삭제가 진행되지 않는다.
  - 타 사용자 소유의 할일에 대해 삭제를 시도(예: API 직접 호출)하면 거부된다(BR-02).
- **완료 조건**: 대상 할일이 목록에서 완전히 제거된다.

### 3.7 카테고리 삭제와 할일 이관

- **관련 UC**: UC-03/UC-04의 전제 기능인 카테고리 관리 (BR-09)
- **사용자 목표**: 지우는 더 이상 쓰지 않는 '아르바이트' 카테고리를 지우고 싶다.
- **사전 조건**: 지우는 '아르바이트' 카테고리와 그 안에 속한 할일 몇 개를 보유하고 있다.
- **시나리오 흐름**:
  1. 지우는 카테고리 관리 화면에서 '아르바이트' 카테고리의 삭제 버튼을 누른다.
  2. 시스템은 삭제를 확인받은 뒤 카테고리를 삭제한다.
  3. 해당 카테고리에 속해 있던 할일들은 모두 '기본' 카테고리로 자동 이관된다(BR-09).
  4. 지우는 할일 목록에서 이관된 할일들이 '기본' 카테고리로 표시되는 것을 확인한다.
- **예외/대안 흐름**:
  - 지우가 '기본' 카테고리 자체를 삭제하려 하면, 삭제 버튼이 비활성화되어 있거나 시도 시 서버에서 거부된다(BR-04).
- **완료 조건**: 카테고리는 삭제되고, 소속 할일은 유실 없이 '기본' 카테고리에서 계속 조회된다.

## 4. 핵심 사용자 여정(User Journey) 요약

지우는 처음 서비스를 접하고 회원가입을 마치면(3.1), 자동 생성된 '기본' 카테고리를 바탕으로 곧바로 할일을 등록할 수 있는 상태가 된다. 이후 지우는 자신의 생활 영역에 맞는 카테고리('과제', '아르바이트' 등)를 직접 만들고 그 아래에 할일을 쌓아간다(3.3). 시간이 지나 할일이 늘어나면 카테고리와 상태 필터를 조합해 지금 집중해야 할 항목을 빠르게 찾아내고(3.4), 진행 상황에 따라 완료 체크나 일정 변경을 반복한다(3.5). 더 이상 필요 없는 할일이나 카테고리는 각각 삭제하거나(3.6) 삭제 시 자동 이관을 통해 정리하며(3.7), 이름이 바뀌는 등 계정 정보가 달라지면 마이페이지에서 수정한다(3.2). 이 여정 전체는 로그인 상태를 전제로 하며, 세션이 만료되면 access_token 재발급(refresh_token) 과정을 거쳐 동일한 흐름이 끊김 없이 이어진다(PRD 6.3절).

## 5. 범위 외 시나리오

다음 항목은 도메인 정의서 8절 및 PRD 3.2절에서 범위 외로 명시된 항목이며, 본 시나리오 문서에서도 다루지 않는다.

- 할일/카테고리를 다른 사용자와 공유하거나 함께 작업하는 시나리오
- 할일 관련 알림(이메일, 푸시 등)을 받는 시나리오
- 할일에 첨부파일을 업로드하는 시나리오
- 할일 우선순위 지정, 반복 일정 등록, 하위 작업(subtask) 관리 시나리오
- 소셜 로그인을 통한 가입/로그인 시나리오
- 모바일 네이티브 앱 전용 사용자 흐름(반응형 웹으로 대체)
