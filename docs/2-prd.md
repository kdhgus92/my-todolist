## 1. 문서 개요

### 1.1 목적

본 문서는 할일 관리 웹 애플리케이션 "my-todolist"의 제품 요구사항을 정의한다. 도메인 개념, 엔티티, 비즈니스 규칙, 유스케이스는 이미 [1-domain-definition.md](./1-domain-definition.md) (v0.3)에 정의되어 있으므로, 본 문서는 이를 중복 서술하지 않고 참조하며 그 위에 제품 범위, 기능/비기능 요구사항, 기술 아키텍처, 일정을 정의한다.

### 1.2 관련 문서

- 도메인 정의서: [docs/1-domain-definition.md](./1-domain-definition.md) — 엔티티(EN-xx), 비즈니스 규칙(BR-xx), 유스케이스(UC-xx) 정의

### 1.3 표기 규칙

본 문서에서 EN-xx, BR-xx, UC-xx는 모두 도메인 정의서의 해당 ID를 가리킨다.

## 2. 제품 개요 및 목표

### 2.1 문제 정의 요약

인증된 사용자별로 개인화된 할일을 관리할 수 있는 서비스가 부재하며, 단순 할일 등록을 넘어 시작일자·종료일자 기준의 진행 상태 추적이 가능한 서비스가 필요하다 (도메인 정의서 2절 참조).

### 2.2 목표 사용자

- 학생 및 20대~50대 직장인. 별도의 상세 페르소나 정의는 본 프로젝트 규모상 생략한다.

### 2.3 비즈니스 목표

- 개인 사용자가 카테고리 기반으로 할일을 등록·조회·관리할 수 있는 웹 서비스를 제공한다.
- 최대 1,000명의 사용자가 동시 접속하여 이용 가능한 서비스 규모를 목표로 한다.

## 3. 범위

### 3.1 MVP 범위

2일이라는 개발 일정 제약상, MVP는 도메인 정의서에 정의된 UC-01 ~ UC-06 전체를 범위로 한다. 별도의 우선순위 조정 없이 6개 유스케이스 모두를 핵심 기능으로 간주한다.

| UC ID | 유스케이스 | MVP 포함 여부 |
|---|---|---|
| UC-01 | 회원가입 / 로그인 (인증) | 포함 |
| UC-02 | 사용자 정보 수정 | 포함 |
| UC-03 | 할일 등록 | 포함 |
| UC-04 | 할일 목록 조회 및 필터링 | 포함 |
| UC-05 | 할일 수정 | 포함 |
| UC-06 | 할일 삭제 | 포함 |

카테고리 생성/조회 자체는 별도 UC로 명시되어 있지 않으나, UC-03(할일 등록 시 카테고리 지정)과 UC-04(카테고리 필터링)의 전제 기능으로서 카테고리 생성·목록조회·삭제 화면/API를 MVP에 포함한다.

### 3.2 범위 외

도메인 정의서 8절(범위 외)을 그대로 따른다: 할일/카테고리 공유·협업, 알림, 첨부파일, 우선순위/반복일정/하위작업, 소셜 로그인. 추가로 본 PRD 수준에서 다음을 명시적으로 범위 외로 확인한다.

- 모바일 네이티브 앱 (반응형 웹으로 대체, 6.1절 참조)
- 접근성(a11y) 대응
- 실사용 환경에서의 부하테스트 및 성능 튜닝 (9절 리스크 참조)

참고로 다크/라이트 모드와 다국어(한/영/일) 지원은 위 MVP 범위에 없었으나, FE-09(전체 수동 통합 테스트) 완료 후 사용자 요청으로 프론트엔드에 추가 구현되었다(구현 상세는 8-plan.md FE-09 이후 범위外 추가 작업 참조).

## 4. 기능 요구사항

기능은 화면/기능 단위로 정리하며, 각 항목은 대응하는 UC를 참조한다.

### 4.1 회원가입 / 로그인 화면 (UC-01)

- 이메일·비밀번호 기반 회원가입 폼을 제공한다.
- 회원가입 성공 시 기본 카테고리가 자동 생성됨을 사용자에게 노출할 필요는 없으나, 신규 할일 등록 시 즉시 사용 가능해야 한다.
- 로그인 폼을 제공하며, 인증 실패 시 사유를 표시한다.
- 로그인 상태가 아닌 사용자는 할일/카테고리/마이페이지 등 인증 필요 화면에 접근할 수 없다(BR-01).

### 4.2 마이페이지 (UC-02)

- 사용자 이름(name) 수정 폼을 제공한다.
- email은 표시만 하고 수정 불가로 처리한다(BR-07).

### 4.3 할일 등록 (UC-03)

- 제목, 시작일자, 종료일자(캘린더 입력), 카테고리 선택 입력을 제공한다.
- 카테고리를 선택하지 않으면 기본 카테고리로 자동 저장된다(BR-03).
- 종료일자가 시작일자보다 이전이면 클라이언트/서버 양쪽에서 등록을 거부하고 오류 메시지를 표시한다(BR-05).

### 4.4 할일 목록 및 필터링 (UC-04)

- 로그인 사용자 본인의 할일만 목록으로 조회한다(BR-02).
- 카테고리별 필터, 상태별 필터(시작전/진행중/완료/기한초과)를 제공한다.
- 상태는 서버 또는 클라이언트에서 조회 시점 기준으로 계산하여 표시한다(BR-06, 도메인 정의서 4.4절).

### 4.5 할일 수정 (UC-05)

- 편집 화면에서 제목·시작일자·종료일자·카테고리·완료 여부를 수정할 수 있다.
- 본인 소유 할일이 아닌 경우 접근/저장을 거부한다(BR-02).
- 종료일자 < 시작일자인 경우 저장을 거부한다(BR-05).

### 4.6 할일 삭제 (UC-06)

- 목록 또는 편집 화면에서 삭제 액션을 제공하며, 삭제 전 확인(confirm) 절차를 둔다.
- 본인 소유 할일이 아닌 경우 삭제를 거부한다(BR-02).

### 4.7 카테고리 관리 (UC-03, UC-04의 전제 기능)

- 카테고리 생성(이름 입력, 사용자별 유일성 검증 — 도메인 정의서 4.2절), 목록 조회, 삭제 기능을 제공한다.
- 기본 카테고리는 목록에 표시하되 삭제 버튼을 비활성화하거나 삭제 시도를 서버에서 거부한다(BR-04).
- 카테고리 삭제 시 해당 카테고리의 할일은 기본 카테고리로 자동 이관된다(BR-09).

## 5. 비기능 요구사항

### 5.1 성능

- 동시 접속 사용자 최대 1,000명을 목표로 한다. 구체적 대응 방안은 7절 참조.
- 목록 조회, 필터링 등 주요 API 응답 시간은 일반적인 사용 환경에서 체감 가능한 지연 없이 처리되는 수준을 목표로 하며, 별도의 정량적 SLA는 설정하지 않는다(1인 2일 개발 규모 고려).

### 5.2 반응형 웹

- 모바일 네이티브 앱은 개발하지 않으며, 웹 화면은 반응형 UI로 구현하여 데스크톱과 모바일 브라우저 모두에서 사용 가능해야 한다.
- 모바일 우선(mobile-first) 설계는 적용하지 않으며, 데스크톱 웹을 기준으로 하되 주요 화면(목록, 등록/수정 폼, 로그인)이 모바일 화면 폭에서도 깨지지 않도록 한다.

### 5.3 보안

- 비밀번호는 평문 저장을 금지하고 해시하여 저장한다(EN-01 password 제약, BR-08 연계).
- 인증되지 않은 사용자의 API 접근을 차단한다(BR-01).
- 모든 할일/카테고리 API는 요청자 소유 여부를 검증한다(BR-02).
- 인증 방식은 6.3절의 JWT 기반 방식을 따른다.

### 5.4 가용성

- 별도의 이중화·다중 리전 구성은 하지 않으며, 단일 인스턴스 운영을 전제로 한다(1인 개발, 예산 제약).
- 장애 발생 시 재기동으로 복구 가능한 수준의 단순한 운영 구조를 목표로 한다.

### 5.5 접근성

- 본 프로젝트에서는 접근성(a11y) 대응을 범위에 포함하지 않는다.

## 6. 기술 아키텍처 개요

### 6.1 플랫폼

- 웹 우선(Web-first). 모바일은 반응형 웹 UI로만 대응하며 별도 모바일 앱은 개발하지 않는다.

### 6.2 기술 스택

| 영역 | 기술 |
|---|---|
| 프론트엔드 | React 19 + TypeScript |
| 전역 상태관리 | Zustand |
| 서버 상태 동기화 | TanStack Query |
| 백엔드 | Node.js + JavaScript + Express |
| DB 액세스 | pg (node-postgres) — ORM 미사용, 직접 SQL/쿼리빌더 사용 |
| 데이터베이스 | PostgreSQL 17 |

- ORM(Prisma 등)을 사용하지 않는 것은 팀/인프라 제약에 따른 결정이며, 스키마가 단순한 4개 엔티티(User, Category, Todo, 상태는 파생값이므로 테이블 없음) 수준이므로 직접 SQL로도 충분히 관리 가능하다.
- Zustand는 로그인 상태 등 클라이언트 전역 상태를, TanStack Query는 할일/카테고리 등 서버 데이터의 캐싱·동기화를 각각 담당하는 역할 분리로 사용한다.

### 6.3 인증 방식

- JWT 기반 인증을 사용하며, access_token과 refresh_token을 함께 발급하는 방식을 채택한다.
- **access_token**: 로그인 성공 시 발급되며, 이후 API 요청의 Authorization 헤더(Bearer)에 포함하여 전송한다. 짧은 만료 시간(예: 15분~1시간)을 적용해 탈취 시 피해 범위를 제한한다.
- **refresh_token**: access_token보다 긴 만료 시간(예: 7일~14일)을 가지며, access_token 만료 시 재발급 용도로만 사용한다. 별도의 refresh 전용 API 엔드포인트를 통해 갱신한다.
- refresh_token은 XSS로부터 상대적으로 안전한 HttpOnly 쿠키에 저장하는 것을 원칙으로 하며, access_token은 클라이언트 메모리(Zustand 등)에 보관하고 저장소(localStorage 등)에 영속화하지 않는다.
- 서버는 세션 상태를 자체 저장하지 않는 stateless 구조로 운영하여, 다중 인스턴스 확장 시에도 별도의 세션 공유 구성이 불필요하도록 한다. refresh_token 자체의 서버 측 저장(화이트리스트/블랙리스트 관리)은 1인 2일 개발 규모상 MVP 범위에서 제외하고, 향후 과제로 남긴다(10절 참조).

## 7. 동시 접속 1,000명 목표에 대한 고려사항

1인 2일 개발 규모에 맞추어 과도한 설계 없이 최소한의 현실적 대응만 적용한다.

- **DB 커넥션 풀링**: pg의 Pool을 사용하여 커넥션을 재사용한다. 풀 크기는 애플리케이션 인스턴스당 적정 수준(예: 10~20)으로 설정하고, PostgreSQL 서버의 max_connections 한도 내에서 운영한다.
- **인덱스**: Todo 테이블의 userId, categoryId 컬럼과 User 테이블의 email(고유 제약) 컬럼에 인덱스를 적용하여 조회 성능을 확보한다.
- **stateless 서버**: JWT 기반 인증으로 서버가 세션을 보유하지 않으므로, 필요 시 인스턴스를 수평으로 늘리는 것만으로 확장이 가능한 구조를 취한다.
- **캐싱**: 별도의 캐싱 레이어(Redis 등)는 MVP 범위에서 도입하지 않는다. 데이터 규모와 개발 기간을 고려할 때 DB 인덱스만으로 충분하다고 판단한다.
- 위 조치는 이론적인 확장 여지를 마련하는 수준이며, 실제 1,000명 동시 접속 상황에서의 성능은 검증되지 않은 상태임을 9절에서 리스크로 명시한다.

## 9. 리스크 및 가정

1인 2일 개발이라는 제약을 솔직하게 반영하여 다음 리스크를 사전에 인지하고 진행한다.

- **테스트 커버리지 부족**: 자동화된 단위/통합 테스트를 충분히 작성할 시간이 없으며, 주로 수동 확인에 의존한다. 배포 후 버그 발생 가능성을 감수한다.
- **부하테스트 미실시**: 동시 접속 1,000명 목표에 대해 실제 부하테스트(k6, JMeter 등)를 수행할 시간적 여유가 없다. 7절의 조치는 이론적 대응이며, 실제 임계치는 검증되지 않는다.
- **에러 처리/예외 케이스 커버리지**: 촉박한 일정상 예상 밖의 입력값이나 경계 조건에 대한 처리가 누락될 수 있다.
- **보안 검토 미흡**: 기본적인 인증/인가(BR-01, BR-02)와 비밀번호 해시는 구현하나, 별도의 보안 취약점 점검(예: 침투테스트)은 수행하지 않는다.
- **인프라 운영**: 배포/모니터링/백업 등 운영 체계는 최소 수준으로만 구성하며, 장애 대응 체계는 갖추지 못한다.
- **가정**: 위 리스크는 MVP 출시 이후 사용량과 피드백에 따라 후속 스프린트에서 보완하는 것을 전제로 한다.

- 도메인 정의서 8절에 명시된 항목(공유/협업, 알림, 첨부파일, 우선순위/반복일정/하위작업, 소셜 로그인)은 향후 과제로 남긴다.
